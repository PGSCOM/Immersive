# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Immersive-2 is an open-source "use your PC monitors in VR" system (an Immersed alternative). It has three independent pieces that talk over a custom TCP/UDP wire protocol:

- **`host/`** — C++ application for Windows, Linux and macOS that captures the desktop (Windows: WGC → DXGI fallback; macOS: ScreenCaptureKit; Linux: xdg-desktop-portal + PipeWire on Wayland, XShm on X11), encodes frames (MJPEG software encoder everywhere; H.264/HEVC/AV1 through `create_hw_encoder()`: Media Foundation on Windows, VideoToolbox on macOS, FFmpeg NVENC → VAAPI → libx264 on Linux), streams them over UDP, captures system audio (WASAPI / ScreenCaptureKit / PulseAudio) and injects mouse/keyboard input from the client (SendInput / CGEvent / RemoteDesktop portal / XTEST).
- **`client/project/`** — Godot 4.7 + OpenXR VR client (Quest / Pico 4) that connects to the host, decodes the stream, and renders monitors as floating 3D panels.
- **`web/`** — experimental WebXR client; `web/bridge/bridge.js` is a Node bridge that re-exposes the native TCP/UDP protocol as HTTP/MJPEG for browsers.

`protocol/protocol.h` is the single shared definition of the wire format (message types, structs) and is included by both the C++ host and conceptually mirrored by the GDScript client. **`docs/PROTOCOL.md` is the human-written reference; it is kept in sync but `protocol.h` still wins when they disagree, so read the header directly when in doubt.** (`protocol/README.md` used to hold a second, drifting copy of that reference — it is now just a pointer.)

## Build / Run Commands

### Host (C++)

```powershell
cd host
cmake -B build -G "Visual Studio 17 2022" -A x64 -DENABLE_NVENC=OFF -DENABLE_AMF=OFF -DENABLE_QSV=OFF
cmake --build build --config Release
.\build\Release\immersive2_host.exe
```

Linux/macOS (real capture/input/audio; dependencies and permissions in `docs/BUILDING.md`). On Linux every backend is optional at configure time — cmake prints `Linux backends: X11=… Wayland-portal=… PulseAudio=…` and builds with whatever it found:

```bash
cd host
cmake -B build -DCMAKE_BUILD_TYPE=Release -DENABLE_NVENC=OFF -DENABLE_AMF=OFF -DENABLE_QSV=OFF
cmake --build build
./build/immersive2_host
```

CMake options `ENABLE_NVENC` / `ENABLE_AMF` / `ENABLE_QSV` default to `ON` but CI and most local dev builds set them `OFF` since the MJPEG software encoder needs no GPU SDK. The host's real entry point/orchestration logic lives in `host/src/main.cpp` (see Architecture below) — there is no unit-test runner; `host/tools/smoke_client.py` and `host/tools/view_only_test.py` (host only) and `host/tools/e2e_test.py` (host + Godot client) are the test suite.

Host CLI flags (see `host/src/main.cpp` `usage()`): `--codec mjpeg|h264|h265|av1`, `--jpeg-quality N` (10–95), `--pin NNNNNN` / `--no-pin` (pairing; default: a random PIN created once in `~/.config/immersive2/pairing-pin` or `%APPDATA%\Immersive2\pairing-pin` — tests always pass `--pin 246810` or `--no-pin` so they never create it), `--no-audio`, `--no-usb` (skip the `adb reverse` upkeep that lets a USB-cabled headset connect to its own 127.0.0.1; see `host/src/usb/adb_reverse.cpp`), `--view-only` (share screens, ignore all input; advertised in discovery and HELLO_ACK), `--max-clients N`, `--tcp-port`, `--udp-port`, `--audio-port`, `--no-ui` (no tray icon, no settings window: every test and CI run passes it), `--panel-port N` (settings panel on 127.0.0.1, default 19803, any free port if busy), `--install-idd-cert` (one-shot, admin-only: trusts a self-signed key so an unsigned IDD driver installs — see `docs/IDD_DRIVER.md`; never runs on its own).

Settings the panel changes (view-only, PIN on/off, default codec, JPEG quality, sound, USB) persist in `host.conf` in that same settings folder; CLI flags override them for one run, and the panel writes back only the key it changed. `--stub` ignores `host.conf` so tests are reproducible.

### Settings panel + tray test

```bash
IM2_TCP_PORT=41800 IM2_UDP_PORT=41801 python3 host/tools/panel_test.py
```

Starts `--stub --no-usb --pin 246810` with a private `HOME`/`XDG_CONFIG_HOME`, no display and an unreachable session bus (nothing can reach the real desktop; the panel URL is read from the log). ### Smoke-testing the host (no headset required)

```bash
./host/build/immersive2_host --stub --pin 246810 &     # fake displays, input only logged
python host/tools/smoke_client.py
```

Connects from `127.0.0.2` (not `127.0.0.1`) so it can bind the UDP video port locally even while the host holds the wildcard bind on the same port — this is the standard trick for exercising the host on a single machine. Because it is not 127.0.0.1 it is *not* trusted, so it also exercises pairing: LAN discovery on UDP 19800, HELLO without / with a wrong PIN (HELLO_REJECT), a request before HELLO (dropped), idle unpaired sockets (dropped, never blocking a real client). Then the HELLO handshake with the PIN, MONITOR_LIST, MULTI_MONITOR_SELECT, frame reassembly, per-monitor downscaling, the codec fallback chain, STREAM_STOP, and a second connection from 127.0.0.1 (trusted, like USB) in TCP media mode that must receive every monitor as in-band `VIDEO_FRAME` messages, get at most a few frames while it stops sending FRAME_ACK, and live frames again once it acks. `IM2_PIN`, `IM2_TCP_PORT` and `IM2_UDP_PORT` override its defaults (as they do for codec_test/x11_test), so several sessions on one machine can test in parallel on different ports.

`--stub` (any OS; `stub_capture.cpp`; monitors 0-1 static like an idle event-driven capture, monitor 2 animated with a bar in its left quarter) reports **three** fake displays of different resolutions (1920x1080, 1920x1200, 1280x720), so this smoke test genuinely covers the multi-monitor paths — three worker threads, per-monitor encoders and the per-monitor mouse-scaling map — rather than a single stream.

### End-to-end test: real host + real Godot client (no headset required)

```bash
python3 host/tools/e2e_test.py        # E2E_VERBOSE=1 to see both logs
```

Linux only. Builds the host (incremental), re-imports the Godot project (class names), starts the host with `--stub --pin 246810 --no-usb` (ports from `IM2_TCP_PORT`/`IM2_UDP_PORT`, default 19800/19801, passed to the client as `--im2-port`/`--im2-udp-port`), and runs the actual client headless (`godot` 4.7 on PATH) with the test-harness args `--im2-host=127.0.0.1 --im2-monitors=0,1,2 --im2-capture`. Checks that all three stub monitors decode onto their own panel (each stub is a distinct grey, reported by the `panel mon=N ... center=RRGGBB` harness line), that the client reconnects after the host is killed and after it freezes (SIGSTOP — exercises the client's 10 s host-silence timeout in `network_client.gd`), that the host's client sockets carry TCP keepalive, and that Ctrl+C exits the host. Step 5 reconnects with `--im2-usb`, the client's USB mode: `adb reverse` tunnels TCP only, so the client sets `HELLO_FLAG_TCP_MEDIA` and the host sends video/audio in-band on the control socket (`VIDEO_FRAME` / `AUDIO_DATA`); on Android a `127.x` host address implies it. Step 6 is automatic USB: a client started on the LAN address with `--im2-usb-port=N` (turns on the USB probe on desktop; the "cable" is 127.0.0.1:N) must move to a local TCP forwarder standing in for `adb reverse` when it appears, back to the LAN when it drops every connection (the pulled cable), and to the forwarder again. Step 7 runs `client/tests/discovery_test.gd` (HostDiscovery finds the running host, with its PIN flag) and then pairing for real over the machine's LAN address: without `--im2-pin` the client must be refused (reason 1) and stop retrying, with it it must stream. Step 8 starts a client with `--im2-virtual=1280x720`: the host must create virtual monitor 100 and the client must stream it (the stub's virtual grey, 208). Step 10 runs `client/tests/overlay_test.gd` under `xvfb-run`: it renders the real in-VR menu offscreen and drives it with the same pointer events the controllers inject (address keypad and validation, the discovered-PC list, PIN entry, tabs, monitor switches, Space/Quality controls, and that each tab fits the fixed 1000x680 panel without scrolling); pass `-- /tmp/shot` to it to get PNGs of each state. Step 11 runs headless: `client/tests/hand_input_test.gd` feeds `hand_input.gd` fake trackers and checks that a pinch clicks where the hand points (fallback ray shoulder → index knuckle, so curling the finger into a pinch cannot move it, and turning or tilting the head does not move it either), that hand shake does not turn a click into a drag, that the runtime's hand-interaction aim pose wins over the fallback and its pinch value clicks when the joints are gone, that a replaced hand tracker (session restart) is followed, bar grabs, menu clicks, and the palm menu (palm to the face shows the mark, a short pinch toggles the menu, a long one or a palm turned away does not); `client/tests/controller_idle_test.gd` drives `vr_input.gd` (trigger click, release reaching the PC even off the screen, short grip = right click vs held grip = grab, hand-over between controllers, bare hands taking the pointer and handing it back, idle hiding); `client/tests/workspace_test.gd` checks ray hits on flat/curved screens, nearest-hit picking and grab bars, LaserDrag (locked to the pointer in position and rotation, level assist, face-me mode, push/pull, reach, followers), the corner resize handles (pick, resize maths, clamp, opposite corner fixed), the snap frame mesh and the VR keyboard's one-shot modifiers; `client/tests/groups_test.gd` checks screen groups, the snap frame offered on each side of a flat or curved neighbour and the landing on release, occupied/far/turned-away sides, and lock; `client/tests/virtual_match_test.gd` the 1:1 size math. Test runs launched with `--im2-host` never write the user's config or workspace. Run the suite after touching the protocol, reconnect, shutdown, menu or input code.

### VR Client (Godot)

Desktop testing (no headset): open `client/project/` in Godot 4.7+, press F5, press `O` to open the overlay and connect.

On a real headset the harness args can't come from `am start` (the launcher drops intent extras): export a test APK with `command_line/extra_args="--im2-host=… --im2-port=… --im2-capture"` added to the Android preset (don't commit it), run a `--stub --no-ui --no-usb` host on free ports, and read `adb logcat -s godot:* Im2VideoDecoder:*` (the `[TEST] debug capture` line carries MJPEG in/out/bad counts; Im2VideoDecoder logs H.264 output frames). Reinstall the normal APK afterwards. Start the adb server detached (`setsid -f adb start-server`) or it dies with the shell that spawned it, taking its `adb reverse` tunnels along.

Export builds:

```bash
godot --headless --path client/project --export-debug "Android" client/dist/immersive2-debug.apk
adb install -r client/dist/immersive2-debug.apk

godot --headless --path client/project --export-debug "Windows Desktop" client/dist/immersive2-debug.exe
```

The Android export bundles the MediaCodec decoder plugin from `addons/im2_decoder/bin/*.aar`, built separately from `client/android-plugin/` (`gradle assembleRelease`, requires Android SDK/NDK; see `client/android-plugin/README.md`). The client has **two decode paths**, chosen per device by codec negotiation:
- **Hardware** (`video_decoder.gd` → MediaCodec, Android/Pico/Quest): H.264/HEVC/AV1, zero-copy into an `ExternalTexture`. Requires the AAR plugin.
- **Software** (`software_video_decoder.gd`, `SoftwareVideoDecoder`): MJPEG decoded on a `WorkerThreadPool` thread via Godot's built-in JPEG decoder — works on **PC (Windows/Linux/macOS desktop), iOS, and web**, no native plugin. The decoded `Image` is uploaded to the panel via `screen_panel.gd::update_decoded_image()`.

`main.gd::_default_codec_for_device()` picks H.264 when `VideoDecoder.is_codec_supported()` (MediaCodec present), else MJPEG, so platforms without the plugin negotiate MJPEG up front (the host always supports the MJPEG software encoder). `_resolve_codec()` also degrades a user-forced HW codec to MJPEG on such platforms, and `_request_codec_fallback()` is the runtime safety net. The plugin must register under the Godot 4.2+ **`org.godotengine.plugin.v2`** manifest prefix — a `v1` prefix is silently ignored and was the cause of a hard fall to MJPEG (≈1 fps). Note: native hardware decode for PC/iOS (Media Foundation / VideoToolbox) is not implemented — those platforms use the software MJPEG path.

## Architecture

### Host: single-process, per-monitor worker threads

`host/src/main.cpp` is the orchestrator — there's no class wiring this together, it's all in `main()`. On startup it builds a capture backend via `create_screen_capture()` (or `create_stub_capture()` with `--stub`) to enumerate displays, checks Media Foundation encoder availability (`mf_encoder_available` for H.264/HEVC/AV1), creates an `InputInjector`, an `IVirtualDisplayManager` (IDD detection), optional loopback `AudioCapture`, and the `NetworkServer`.

Each selected monitor gets its own OS thread (`stream_worker` lambda) with its own capture + encoder instance, registered in `active_streams` (keyed by monitor id, guarded by `streams_mutex`). Monitor selection changes (`apply_selection`) diff the requested set against `active_streams`: stop threads no longer wanted, join them, start new ones. A `STREAM_CONFIG` that changes codec or `max_width` tears down and respins all active streams, sending `STREAM_STOP` for each first so the client rebuilds its panel and decoder from the following `STREAM_START`; one that only changes bitrate / JPEG quality / fps is handed to the running workers (`ActiveStream::new_cfg`), which call `IVideoEncoder::reconfigure()` (live in every backend; VAAPI re-opens at the same size, an IDR, so automatic raises wait until they add up to 25 % or reach the ceiling; a backend that refuses is re-`initialize()`d) — no STREAM_STOP/START.

Adaptive rate: the client's bitrate / JPEG quality are ceilings. `server.cpp` keeps a per-client `RateControl` fed by FRAME_ACKs (skipped frames = loss, send-to-ACK delay > 250 ms = queue, no ACK for 1.5 s = stall): ×0.7 per bad second, +10 %+2 % per clean second after 4 s, starting at 0.5; `link_rate_scale()` exposes it and each worker's `retune()` polls it every 500 ms (MJPEG also drops fps below half the ceiling). The worker also times scale+encode of freshly captured frames and paces a software encoder (libx264, MJPEG; never a GPU one, where it only lost frames and re-opened VAAPI) at what it sustains (15 % headroom), waking for a held frame when it is due; a CPU H.264 encoder (libx264) defaults to 30 fps (measured ~22 ms per 1920x1200 frame, superfast, on the dev laptop). On-demand IDRs are at most one per 200 ms per stream. `smoke_client.py` checks both: a quality-only STREAM_CONFIG must not restart, and a client that stops ACKing must see the rate fall and climb back.

USB (`usb/adb_reverse.cpp`): `start_adb()` finds adb (PATH, then the Android SDK's usual folders) and starts its server before any socket exists; `keep_adb_reverse()` runs on its own thread and every 3 s arms `adb -s <serial> reverse tcp:<port> tcp:<port>` on each authorised device lacking it, logging state changes only. Server sockets are close-on-exec / non-inheritable, so an adb daemon started later cannot keep the port bound after the host exits. In TCP media mode (server.cpp) the socket has TCP_NODELAY and a 1 MB send buffer, and each monitor may have at most 4 frames sent but not yet FRAME_ACKed; beyond that whole frames are dropped (the client's gap detection asks for a keyframe).

Pairing (server.cpp): nothing but HELLO is served until the HELLO passes `check_pin()` — 127.0.0.1 is trusted (local processes, `adb reverse`), everyone else must send `ServerConfig::pin`; wrong PINs cost 0.5 s and 5 lock the address out for a minute; unpaired sockets get a 5 s receive timeout and don't count toward `--max-clients`. A refused HELLO (missing/wrong PIN, not a lock-out) fires `set_on_pin_requested`, and `main.cpp` shows the PIN in a desktop notification (notify-send / osascript / MessageBoxA; throttled to one per 5 s) so the person can read it without the panel. The monitor list and AUDIO_START follow the HELLO_ACK (on_connected_ fires then, not at accept). A discovery thread answers `DiscoveryRequest` broadcasts on UDP `<tcp_port>`. Input callbacks only accept the client that owns the streams, and the host releases held buttons/keys when that client goes away. Frame numbers keep growing across restarts of a monitor's stream (`frame_high_water`), and STREAM_START carries `first_frame`, so the client can drop late frames of the previous stream.

Per-stream codec resolution follows a fallback chain, both at the CLI-default level and per-stream: requested codec (H.264/H.265/AV1 via `create_hw_encoder()`) → H.264 → software MJPEG (`stb_image_write`, always available). The effective codec actually used is announced back to the client in `StreamStart.codec`, which may differ from what was requested.

Mouse input arrives in *stream* pixel coordinates (which can be downscaled from native via `STREAM_CONFIG.max_width`); `main.cpp` keeps a per-monitor `input_scale` map to convert back to native pixels before calling `InputInjector::inject_mouse`.

Each stream worker makes its own capture instance, so backends only ever serve one monitor per instance. The worker restarts a capture that reports `is_capturing() == false` (monitor unplugged, screen-share revoked) and rescales any frame whose size differs from the announced stream size (unless the encoder `scales_input()`; captures that can scale for free honour the `set_output_size()` hint). Event-driven captures deliver nothing on a static desktop, so the worker keeps the newest frame: a frame skipped by FPS pacing is sent once the pacing allows, a REQUEST_KEYFRAME re-encodes it as an IDR at once, after a change or an IDR an inter codec re-encodes it as 30 P-frames at the paced rate (refinement: a still screen otherwise stays at the blurred quality an IDR or a moving frame got, ~30 dB PSNR on text against ~54 refined), and an idle stream re-sends it every second as a P-frame (keepalive; a lost last frame shows the client a gap there). There is no periodic IDR (the encoder GOP is a 60 s safety ceiling): each one blurred the picture again. VAAPI runs VBR, not CBR (Intel's iHD pads every CBR frame to bitrate/fps: 41 666 bytes per still 1080p frame at 20 Mbps). The `--stub` capture mimics that (one frame, then nothing), so the tests exercise this path. Keyboard `scancode` is a Windows VK code on every OS; `main.cpp` presses Shift/Ctrl/Alt around a key from the client's `modifiers` bits (the VR keyboard latches them locally), and non-Windows injectors translate VKs (`input/vk_keysym.h` for X11/Wayland, a kVK table in `mac_input.mm`).

Source layout: `capture/` (`wgc_capture.cpp`/`dxgi_capture.cpp` Windows, `mac_capture.mm`, `x11_capture.cpp`, `portal_session.cpp` + `pipewire_capture.cpp` for Wayland, `linux_backends.cpp` = which Linux backend runs, `stub_capture.cpp`), `encoder/` (`encoder.cpp` = MJPEG software path, `mf_encoder.cpp` = Media Foundation HW path for NVENC/AMF/QSV, `vt_encoder.mm` = VideoToolbox, `ffmpeg_encoder.cpp` = Linux NVENC/VAAPI/libx264; all obey the output contract documented in `encoder.h` — one access unit per `encode()`, Annex-B/OBU, parameter sets on every IDR, no B-frames, BT.601 limited), `network/` (`server.cpp` — TCP control channel, UDP packetisation and send, flow control), `input/` (`input_injector.cpp` SendInput, `mac_input.mm`, `x11_input.cpp`, `portal_input.cpp`), `driver/` (`idd_manager.cpp` — IDD virtual-display detection, see below), `audio/` (`audio_capture.cpp` WASAPI, `mac_audio_capture.mm`, `pulse_audio_capture.cpp`), `ui/` (the persistent UI, see `docs/ARCHITECTURE.md`: `host_ui.h` = live `Settings` atomics + the `Hooks` main.cpp lends, `panel.cpp` + `panel.html` = the settings page on 127.0.0.1 with token/cookie/Origin/Host checks — the page and the Grotesk font are embedded at build time by `embed.cmake`, `tray_win.cpp`/`tray_mac.mm`/`tray_linux.cpp` = tray icons, `ui_platform.cpp` = opening the app window and start at login (filesystem calls there use the `error_code` overloads: an unreadable `~/.config/autostart` means "off", never a crash), `ui_common.cpp` = host.conf, PIN file, second-launch handoff, the tray mark rasteriser). `src/` is on the include path for private headers shared between backends.

On a Wayland session capture and input share one process-wide portal session (`portal_session.cpp`, libdbus): RemoteDesktop+ScreenCast, persisted with a restore token in `~/.config/immersive2/portal-restore-token` so only the first run shows the dialog; X11 is never used as a silent fallback there (it would capture black). Virtual displays made on a headset's request (`IVirtualDisplayManager` in `driver/idd_manager.h`, ids from `VIRTUAL_MONITOR_ID_BASE` = 100, at most 4, removed on exit): X11 adds RandR 1.5 monitors (`x11_capture.cpp`, the screen grows to the right), GNOME Wayland uses Mutter's ScreenCast RecordVirtual (`mutter_virtual.cpp`), macOS the private `CGVirtualDisplay` looked up at run time (`mac_capture.mm`, untested: CI only compiles it), `--stub` fakes them in grey 208; Windows and other desktops answer VDISPLAY_UNSUPPORTED. IDD detection is Windows-only.

### IDD virtual display detection

`idd_manager.cpp` looks for a device whose hardware ID starts with `Root\VID_IDD` via `SetupDiGetDeviceRegistryProperty(SPDRP_HARDWAREID)`, with a secondary fallback check for any monitor device whose friendly name contains "virtual". If neither matches, `is_driver_installed()` returns false and the host just uses physical monitors — this is optional, not required for normal operation. `is_driver_installed()` is a pure query; the signature-trust bypass lives in `install_idd_signing_certificate()` and only runs from `--install-idd-cert`. Driver install/build instructions are in `docs/IDD_DRIVER.md` (it relies on a third-party community driver, `itsmikethetech/Virtual-Display-Driver`, and Windows test-signing).

### VR Client (Godot)

`client/project/scripts/main.gd` is the scene controller: connection state, auto-reconnect (to the last PC, following it via discovery if its IP changes), PIN pairing (pins per PC in the config's `[pairing]`), monitor selection, the arc arrangement / recenter (`pose_recentered` too), and automatic workspace persistence (layouts per monitor id, kept across STREAM_STOP/START so quality changes don't move screens; a saved layout far off the gaze is swung back in front). It is the only writer of `user://immersive2_config.cfg`. `host_discovery.gd` lists PCs from UDP broadcast replies. Automatic USB: on Android (or with `--im2-usb-port`) `usb_probe.gd` sends a HELLO to 127.0.0.1:<port> every 2 s unless already on the cable or the user pressed Disconnect; a HELLO_ACK makes `main.gd` move the session there (`_switch_to`, handled like a drop so screens stay), and losing the USB session falls straight back to `_lan_ip` (the PC's network address, which is also what the config keeps as `host_ip`). At launch it waits for the first probe before auto-connecting over Wi-Fi. The menu's status line says "over USB" / "over Wi-Fi". `screen_panel.gd` builds each screen's mesh itself — a flat quad or a cylinder section whose arc is `curvature × 1.75 rad` — and does the matching ray/cylinder hit test; the shaders only round the corners (no ALPHA write: screens are opaque). `laser_drag.gd` moves screens, menu and keyboard: by default rigidly locked to the pointer (the transform relative to it at grab time stays constant, position and rotation including roll; a roll or pitch within `LEVEL_DEG` of level eases flat), or, with the Input tab's "Screens face me while moving" on, the grabbed point stays on the ray and the thing turns to face the head (upright); reaching out/in with the hand pushes/pulls ×3.5; lightly smoothed; a screen group's other members follow rigidly. `grab_bar.gd` is the bar under each screen, the menu and the keyboard: trigger or pinch on it to move its owner. `resize_handle.gd` is a bracket outside each screen corner (shown when the ray passes near, zone outside the screen so the desktop's corner pixels stay the desktop's): `pick()` returns it as a `bar` hit, so grabbing it goes through the same `LaserDrag.grab()`, and dragging resizes the screen keeping its aspect ratio and the opposite corner fixed (width clamped to `ScreenPanel.MIN_WIDTH`..`MAX_WIDTH`, saved with the layout). `main.gd::pick()` is the one ray test both input paths use: the NEAREST of menu, keyboard, screens and bars. Screen groups ("Move together", per monitor, in the workspace JSON v3), the snap preview and "Lock screens in place" live in main.gd (`drag_group_for`, `snap_target_for`, `on_panel_drag_ended`, `can_move_panel`): while a screen is dragged near a free side of another (`SNAP_CAPTURE_M`), `snap_frame.gd` draws a thin white frame where it would land (`ScreenPanel.landing_beside()`, same orientation, a curved screen continues its arc), and releasing lands it there; snapping never links screens. `match_virtual_screen()` replaces a virtual screen with one sized 1:1 for the headset at its current size and distance (`_headset_ppd()`, `one_to_one_size()`); auto quality uses the screen the pointer was last on. `world.gd` + `sky.gdshader`/`floor.gdshader` are the surroundings. `ui_theme.gd` holds the palette/type shared with the web page (Grotesk from Velvetyne, SIL OFL, in `fonts/`, for the wordmark and big titles only). `network_client.gd` rebinds its UDP socket to the `udp_port` in HELLO_ACK (the host's real port, not the config's) and forgives a gap in its own `_process` ticks (headset asleep) instead of declaring the host silent. `network_client.gd` owns the TCP control connection + UDP video/audio sockets and latency probing. `screen_panel.gd` is a draggable/resizable 3D panel; `main.gd` owns one `video_decoder.gd` per monitor stream. `video_decoder.gd` wraps the `Im2VideoDecoder` Android plugin (MediaCodec) in a **zero-copy** path: MediaCodec decodes straight into a Godot `ExternalTexture` (a `GL_TEXTURE_EXTERNAL_OES` object) via a `SurfaceTexture`, and the panel's `screen_external.gdshader` samples it through `samplerExternalOES` — no CPU readback, no YUV unpacking. `SurfaceTexture.attachToGLContext`/`updateTexImage` must run on Godot's render thread, so they are scheduled via `RenderingServer.call_on_render_thread()` (driven each frame from `main.gd._update_decoders`). Each tick latches every frame pending in the SurfaceTexture (its queue can hold several and `updateTexImage` takes the oldest; the newest stays), and the codec is configured with `low-latency` plus Qualcomm's `vendor.qti-ext-dec-low-latency.enable` / `picture-order.enable` (the Pico 4 runs Android 10, before KEY_LOW_LATENCY), plain if refused; the `consumed frame` logcat line says how many frames were passed over and whether low-latency took. `VideoDecoder.is_codec_supported()` returns false without the plugin (PC/iOS/web); there `main.gd` instead opens a `SoftwareVideoDecoder` (`software_video_decoder.gd`) that decodes the MJPEG stream on a `WorkerThreadPool` thread and uploads the result via `screen_panel.gd::update_decoded_image()` — `_update_decoders` polls both decoder kinds each frame. `vr_input.gd` (one per controller; the last one whose trigger was pressed owns the pointer) / `hand_input.gd` handle controller and hand-tracking pointer input (the controller ray tilt and the pointing hand are Input-tab settings). Bare hands win over controllers whenever the runtime reports one (`hand_input.gd::is_hand()`: the side's controller tracker is on `/interaction_profiles/ext/hand_interaction_ext`, or its XRHandTracker has camera data; trackers are looked up every frame, never cached, since Godot replaces them on a session restart); the runtime decides the switch (Pico: put the controllers down, with auto switch on in its settings). The hand ray is the runtime's aim pose from XR_EXT_hand_interaction (project setting `hand_interaction_profile`, the `pinch` action), else a shoulder → knuckle ray whose shoulder hangs off a neck pivot and a lazy torso yaw. The other hand's palm turned to the face shows a menu mark; a short pinch toggles the menu. Both scripts print what the runtime reports when it changes (`[HandInput]` / `[VRInput]` in `adb logcat -s godot`); `ui_overlay.gd` is the in-VR menu (tabs Connect / Screens / Space / Quality / Input, PIN keypad; holds no settings, main.gd pushes them in); `virtual_keyboard.gd` is the VR keyboard (a 2D UI in a SubViewport; one-shot Shift/Ctrl/Alt/Win, key repeat); `key_map.gd` maps a Bluetooth keyboard's keys to VK codes (forwarded on Android only — on a PC client the keyboard already belongs to a PC). Controller vibration goes through the `haptic` action (action_type 4, `/user/hand/*/output/haptic` in every profile of `openxr_action_map.tres`) via `vr_input.gd::_buzz()`, gated by `main.gd::haptics_enabled`. `main.gd::_can_control()` (the user's "Control this PC" switch and the host's HOST_FLAG_VIEW_ONLY) gates every mouse/keyboard send. With "Sharper text" on and a runtime that composites layers natively, each `screen_panel.gd` drives an `OpenXRCompositionLayerCylinder`/`Quad` placed under XROrigin3D (fed from a SubViewport: the CPU texture, or the OES texture through `screen_layer_external.gdshader`), hole-punched behind Godot's projection layer, with its own mesh hidden (`layers = 0`) but still used for ray hits — untested on a headset, so it is opt-in. Virtual screens: the menu asks via VIRTUAL_DISPLAY_CREATE; `main.gd` shows the new monitor once both VIRTUAL_DISPLAY_RESULT and the re-sent MONITOR_LIST (per-monitor flags byte, MONITOR_FLAG_VIRTUAL) have arrived; `--im2-virtual=WxH` does that from the command line for tests; `audio_receiver.gd` decodes the UDP PCM audio stream into an `AudioStreamGenerator`.

The Android decoder plugin is a separate Gradle/Java project at `client/android-plugin/` (not part of the Godot project tree) producing an AAR consumed via the `addons/im2_decoder` export plugin (an `EditorExportPlugin` that adds the AAR via `_get_android_libraries`).

### Protocol

TLV control messages over TCP (`uint8 type, uint32 length LE, payload`), chunked binary frames over UDP (monitor id, frame number, chunk index/count, ≤1400-byte payload). Default ports: TCP 19800 (control), UDP 19801 (video), UDP 19802 (audio, PCM-16 stereo 48kHz). All message types/struct layouts are defined once in `protocol/protocol.h` — extend that file first when adding a new message, then mirror the struct packing manually in GDScript (the client has no codegen from the header).

## Code Style (from CONTRIBUTING.md)

- **C++ (host):** C++17, `snake_case` functions/variables, `PascalCase` classes/types, `SCREAMING_SNAKE_CASE` constants, trailing/leading `_` for private members, `#pragma once` guards.
- **GDScript (client):** follow the official GDScript style guide, use type hints, document public functions with `##` doc comments.
