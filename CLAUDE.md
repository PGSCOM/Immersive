# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Immersive-2 is an open-source "use your PC monitors in VR" system (an Immersed alternative). It has three independent pieces that talk over a custom TCP/UDP wire protocol:

- **`host/`** — C++ application for Windows, Linux and macOS that captures the desktop (Windows: WGC → DXGI fallback; macOS: ScreenCaptureKit; Linux: xdg-desktop-portal + PipeWire on Wayland, XShm on X11), encodes frames (MJPEG software encoder everywhere; H.264/HEVC/AV1 through `create_hw_encoder()`: Media Foundation on Windows, VideoToolbox on macOS, FFmpeg NVENC → VAAPI → libx264 on Linux), streams them over UDP, captures system audio (WASAPI / ScreenCaptureKit / PulseAudio) and injects mouse/keyboard input from the client (SendInput / CGEvent / RemoteDesktop portal / XTEST).
- **`client/project/`** — Godot 4.7 + OpenXR VR client (Quest / Pico 4) that connects to the host, decodes the stream, and renders monitors as floating 3D panels.
- **`web/`** — experimental WebXR client; `web/bridge/bridge.js` is a Node bridge that re-exposes the native TCP/UDP protocol as HTTP/MJPEG for browsers.

Several headsets can also share a **multiplayer room** (avatars, voice, watching each other's screens; no server): the room runs between the Godot clients (ENet), and each PC streams its shared screens straight to the others as *watchers* (`protocol.h` WATCH_CODE / `HELLO_FLAG_WATCH`). See "Multiplayer rooms" under Architecture.

`protocol/protocol.h` is the single shared definition of the wire format (message types, structs) and is included by both the C++ host and conceptually mirrored by the GDScript client. **`docs/PROTOCOL.md` is the human-written reference; it is kept in sync but `protocol.h` still wins when they disagree, so read the header directly when in doubt.** (`protocol/README.md` used to hold a second, drifting copy of that reference — it is now just a pointer.)

## Build / Run Commands

### Host (C++)

```powershell
cd host
cmake -B build -G "Visual Studio 17 2022" -A x64 -DENABLE_NVENC=OFF -DENABLE_AMF=OFF -DENABLE_QSV=OFF
cmake --build build --config Release
.\build\Release\immersive2_host.exe
```

Linux/macOS (real capture/input/audio; dependencies and permissions in `docs/BUILDING.md`). On Linux every backend is optional at configure time — cmake prints `Linux backends: X11=… Wayland-portal=… PulseAudio=…` and builds with whatever it found:

```bash
cd host
cmake -B build -DCMAKE_BUILD_TYPE=Release -DENABLE_NVENC=OFF -DENABLE_AMF=OFF -DENABLE_QSV=OFF
cmake --build build
./build/immersive2_host
```

CMake options `ENABLE_NVENC` / `ENABLE_AMF` / `ENABLE_QSV` default to `ON` but CI and most local dev builds set them `OFF` since the MJPEG software encoder needs no GPU SDK. The host's real entry point/orchestration logic lives in `host/src/main.cpp` (see Architecture below) — there is no unit-test runner; `host/tools/smoke_client.py`, `host/tools/view_only_test.py`, `host/tools/watch_test.py` and `host/tools/tls_test.py` (host only) and `host/tools/e2e_test.py` (host + Godot client) are the test suite.

Host CLI flags (see `host/src/main.cpp` `usage()`): `--codec mjpeg|h264|h265|av1`, `--jpeg-quality N` (10–95), `--pin NNNNNN` / `--no-pin` (pairing; default: a random PIN created once in `~/.config/immersive2/pairing-pin` or `%APPDATA%\Immersive2\pairing-pin` — tests always pass `--pin 246810` or `--no-pin` so they never create it), `--no-audio`, `--no-usb` (skip the `adb reverse` upkeep that lets a USB-cabled headset connect to its own 127.0.0.1; see `host/src/usb/adb_reverse.cpp`), `--view-only` (share screens, ignore all input; advertised in discovery and HELLO_ACK), `--max-clients N`, `--tcp-port`, `--udp-port`, `--audio-port`, `--no-ui` (no tray icon, no settings window: every test and CI run passes it), `--allow-plaintext` (let headsets on the network connect without TLS: old app versions; off by default, see `docs/SECURITY.md`), `--panel-port N` (settings panel on 127.0.0.1, default 19803, any free port if busy), `--install-idd-cert` (one-shot, admin-only: trusts a self-signed key so an unsigned IDD driver installs — see `docs/IDD_DRIVER.md`; never runs on its own).

The PC's TLS identity (`identity-key.pem`, user-only, and `identity-cert.pem`) is made once in that folder too; tests start the host with a private `XDG_CONFIG_HOME`/`HOME` (`smoke_client.private_config()`, e2e's `HOST_HOME`) so they never create the user's. Settings the panel changes (view-only, PIN on/off, default codec, JPEG quality, sound, USB) persist in `host.conf` in that same settings folder; CLI flags override them for one run, and the panel writes back only the key it changed. `--stub` ignores `host.conf` so tests are reproducible.

### Smoke-testing the host (no headset required)

```bash
./host/build/immersive2_host --stub --pin 246810 &     # fake displays, input only logged
python host/tools/smoke_client.py
```

Connects from `127.0.0.2` (not `127.0.0.1`) so it can bind the UDP video port locally even while the host holds the wildcard bind on the same port — this is the standard trick for exercising the host on a single machine. Because it is not 127.0.0.1 it is *not* trusted, so it also exercises pairing: LAN discovery on UDP 19800, HELLO without / with a wrong PIN (HELLO_REJECT), a request before HELLO (dropped), idle unpaired sockets (dropped, never blocking a real client). Then the HELLO handshake with the PIN, MONITOR_LIST, MULTI_MONITOR_SELECT, frame reassembly, per-monitor downscaling, the codec fallback chain, STREAM_STOP, and a second connection from 127.0.0.1 (trusted, like USB) in TCP media mode that must receive every monitor as in-band `VIDEO_FRAME` messages, get at most a few frames while it stops sending FRAME_ACK, and live frames again once it acks. `IM2_PIN`, `IM2_TCP_PORT` and `IM2_UDP_PORT` override its defaults (as they do for codec_test/x11_test), so several sessions on one machine can test in parallel on different ports.

`--stub` (any OS; `stub_capture.cpp`; monitors 0-1 static like an idle event-driven capture, monitor 2 animated with a bar in its left quarter) reports **three** fake displays of different resolutions (1920x1080, 1920x1200, 1280x720), so this smoke test genuinely covers the multi-monitor paths — three worker threads, per-monitor encoders and the per-monitor mouse-scaling map — rather than a single stream.

### VR Client (Godot)

Desktop testing (no headset): open `client/project/` in Godot 4.7+, press F5, press `O` to open the overlay and connect.

On a real headset the harness args can't come from `am start` (the launcher drops intent extras): export a test APK with `command_line/extra_args="--im2-host=… --im2-port=… --im2-capture"` added to the Android preset (don't commit it), run a `--stub --no-ui --no-usb` host on free ports, and read `adb logcat -s godot:* Im2VideoDecoder:*` (the `[TEST] debug capture` line carries MJPEG in/out/bad counts; Im2VideoDecoder logs H.264 output frames). Reinstall the normal APK afterwards. Start the adb server detached (`setsid -f adb start-server`) or it dies with the shell that spawned it, taking its `adb reverse` tunnels along.

Export builds:

```bash
godot --headless --path client/project --export-debug "Android" client/dist/immersive2-debug.apk
adb install -r client/dist/immersive2-debug.apk

godot --headless --path client/project --export-debug "Windows Desktop" client/dist/immersive2-debug.exe
```

The Android export bundles the MediaCodec decoder plugin from `addons/im2_decoder/bin/*.aar`, built separately from `client/android-plugin/` (`gradle assembleRelease`, requires Android SDK/NDK; see `client/android-plugin/README.md`). The client has **two decode paths**, chosen per device by codec negotiation:
- **Hardware** (`video_decoder.gd` → MediaCodec, Android/Pico/Quest): H.264/HEVC/AV1, zero-copy into an `ExternalTexture`. Requires the AAR plugin.
- **Software** (`software_video_decoder.gd`, `SoftwareVideoDecoder`): MJPEG decoded on a `WorkerThreadPool` thread via Godot's built-in JPEG decoder — works on **PC (Windows/Linux/macOS desktop), iOS, and web**, no native plugin. The decoded `Image` is uploaded to the panel via `screen_panel.gd::update_decoded_image()`.

`main.gd::_default_codec_for_device()` picks H.264 when `VideoDecoder.is_codec_supported()` (MediaCodec present), else MJPEG, so platforms without the plugin negotiate MJPEG up front (the host always supports the MJPEG software encoder). `_resolve_codec()` also degrades a user-forced HW codec to MJPEG on such platforms, and `_request_codec_fallback()` is the runtime safety net. The plugin must register under the Godot 4.2+ **`org.godotengine.plugin.v2`** manifest prefix — a `v1` prefix is silently ignored and was the cause of a hard fall to MJPEG (≈1 fps). Note: native hardware decode for PC/iOS (Media Foundation / VideoToolbox) is not implemented — those platforms use the software MJPEG path.

## Architecture

### Host: single-process, per-monitor worker threads

`host/src/main.cpp` is the orchestrator — there's no class wiring this together, it's all in `main()`. On startup it builds a capture backend via `create_screen_capture()` (or `create_stub_capture()` with `--stub`) to enumerate displays, checks Media Foundation encoder availability (`mf_encoder_available` for H.264/HEVC/AV1), creates an `InputInjector`, an `IVirtualDisplayManager` (IDD detection), optional loopback `AudioCapture`, and the `NetworkServer`.

Each selected monitor gets its own OS thread (`stream_worker` lambda) with its own capture + encoder instance, registered in `active_streams` (keyed by monitor id, guarded by `streams_mutex`). Monitor selection changes (`apply_selection`) diff the requested set against `active_streams`: stop threads no longer wanted, join them, start new ones. A `STREAM_CONFIG` that changes codec or `max_width` tears down and respins all active streams, sending `STREAM_STOP` for each first so the client rebuilds its panel and decoder from the following `STREAM_START`; one that only changes bitrate / JPEG quality / fps is handed to the running workers (`ActiveStream::new_cfg`), which call `IVideoEncoder::reconfigure()` (live in every backend; VAAPI re-opens at the same size, an IDR, so automatic raises wait until they add up to 25 % or reach the ceiling; a backend that refuses is re-`initialize()`d) — no STREAM_STOP/START.

Adaptive rate: the client's bitrate / JPEG quality are ceilings. `server.cpp` keeps a per-client `RateControl` fed by FRAME_ACKs (skipped frames = loss, send-to-ACK delay > 250 ms = queue, no ACK for 1.5 s = stall): ×0.7 per bad second, +10 %+2 % per clean second after 4 s, starting at 0.5 (1.0 over USB); `link_rate_scale()` exposes it and each worker's `retune()` polls it every 500 ms (MJPEG also drops fps below half the ceiling). The worker also times scale+encode of freshly captured frames and paces a software encoder (libx264, MJPEG; never a GPU one, where it only lost frames and re-opened VAAPI) at what it sustains (15 % headroom), waking for a held frame when it is due; a CPU H.264 encoder (libx264) defaults to 30 fps (measured ~22 ms per 1920x1200 frame, superfast, on the dev laptop). On-demand IDRs are at most one per 200 ms per stream. The VBV (`EncoderConfig::vbv_kbit`, `vbv_bits()`, starting full) alone decides how big, so how sharp, an IDR is: `main.cpp` gives USB 8 Mbit (at most 400 ms of the rate) and UDP 4 Mbit (200 ms) — measured on hevc_vaapi with a 1920x1200 page of text, 0.6 Mbit gave a 19 dB IDR and ~20 blurred frames, 8 Mbit 58 dB at once. `smoke_client.py` checks both: a quality-only STREAM_CONFIG must not restart, and a client that stops ACKing must see the rate fall and climb back.

USB (`usb/adb_reverse.cpp`): `start_adb()` finds adb (PATH, then the Android SDK's usual folders) and starts its server before any socket exists; `keep_adb_reverse()` runs on its own thread and every 3 s arms `adb -s <serial> reverse tcp:<port> tcp:<port>` on each authorised device lacking it, logging state changes only. Server sockets are close-on-exec / non-inheritable, so an adb daemon started later cannot keep the port bound after the host exits. In TCP media mode (server.cpp) the socket has TCP_NODELAY and a 1 MB send buffer, and once a monitor's oldest frame sent but not yet FRAME_ACKed has waited 150 ms, whole frames are dropped (the client's gap detection asks for a keyframe); by age, not count, so a big sharp IDR on the cable does not turn the frames behind it into a gap.

Encryption (`network/tls.cpp`, mbedTLS 3.6 LTS fetched by CMake with its SHA-256; `docs/SECURITY.md`): a connection whose first byte is `0x16` gets a TLS 1.2 handshake (ECDHE-ECDSA, AEAD suites only) with the PC's identity (`tls::Identity`: ECDSA P-256, self-signed `CN=immersive-host`, fingerprint = first 8 bytes of SHA-256 of the DER, printed, in the panel and the PIN notification); then IDENTITY (the PEM) goes before the answer to the HELLO, and after the PIN a random `MEDIA_KEY` (`tls::MediaCipher`: AES-128-CBC + HMAC-SHA-256, 16-byte tag, IVs from AES of a counter) seals every UDP datagram to that client, video and audio. Plain TCP is only accepted from 127.0.0.0/8 (the cable, local tools; IDENTITY on `HELLO_FLAG_IDENTITY`) unless `--allow-plaintext`, else REJECT_ENCRYPTION_REQUIRED (5). mbedTLS has no threading here: handshakes run one step at a time under a global mutex with a non-blocking receive BIO, each session has its own mutex, the RNG another. Each control message is one write (one TLS record). Pairing (server.cpp): nothing but HELLO is served until the HELLO passes `check_pin()` — 127.0.0.1 is trusted (local processes, `adb reverse`), everyone else must send `ServerConfig::pin`; wrong PINs cost 0.5 s and 5 lock the address out for a minute; past 20 wrong ones in a minute from all addresses together each costs 5 s (with a warning at most every 10 minutes: slower, never locked, so nobody can keep the real headset out); unpaired sockets get a 5 s receive timeout and don't count toward `--max-clients`. A refused HELLO (missing/wrong PIN, not a lock-out) fires `set_on_pin_requested`, and `main.cpp` shows the PIN in a desktop notification (notify-send / osascript / MessageBoxA; throttled to one per 5 s) so the person can read it without the panel. The monitor list and AUDIO_START follow the HELLO_ACK (on_connected_ fires then, not at accept). A discovery thread answers `DiscoveryRequest` broadcasts on UDP `<tcp_port>`. Watchers (multiplayer): a client's WATCH_CODE lets headsets that send it in a `HELLO_FLAG_WATCH` HELLO (`accept_watcher`, same cost/lock-out as a PIN, not counted in `--max-clients`) watch that client's screens: each stream worker keeps a `WatchStream` (main.cpp) that, while anybody watches (`has_watchers`), takes a copy of the frames it sends at most 8 times a second and, on a thread of its own, scales it to at most 1280 wide and encodes it as MJPEG (every client decodes it, a PC too), sent with `send_watch_start`/`send_watch_packet` to every watcher's own UDP port (`Hello.udp_port`; FEC as usual, `send_udp_frame`); STREAM_STOP reaches them too and late watchers get the live watch STREAM_STARTs (`stream_starts_`). The owner's stream never depends on watchers. A watcher gets no monitor list or audio, and only its LATENCY_PROBE and PING are acted on; a new code, code 0 or the owner leaving drop them. HELLO_ACK carries `lan_ipv4` (`primary_ipv4()`) so a headset on the cable can tell its room where to watch from. Input callbacks only accept the client that owns the streams, and the host releases held buttons/keys when that client goes away. Frame numbers keep growing across restarts of a monitor's stream (`frame_high_water`), and STREAM_START carries `first_frame`, so the client can drop late frames of the previous stream.

Per-stream codec resolution follows a fallback chain, both at the CLI-default level and per-stream: requested codec (H.264/H.265/AV1 via `create_hw_encoder()`) → H.264 → software MJPEG (`stb_image_write`, always available). The effective codec actually used is announced back to the client in `StreamStart.codec`, which may differ from what was requested. H.264 streams stay inside Level 5.2 (`fit_h264`: 4096 a side, as VAAPI and the Pico's decoder take, and 36864 macroblocks), so a bigger monitor (a 5120x1440 virtual screen) streams scaled down in `StreamStart`; HEVC/AV1 carry the host's whole 7680x4320.

Mouse input arrives in *stream* pixel coordinates (which can be downscaled from native via `STREAM_CONFIG.max_width`); `main.cpp` keeps a per-monitor `input_scale` map to convert back to native pixels before calling `InputInjector::inject_mouse`.

Each stream worker makes its own capture instance, so backends only ever serve one monitor per instance. The worker restarts a capture that reports `is_capturing() == false` (monitor unplugged, screen-share revoked) and rescales any frame whose size differs from the announced stream size (unless the encoder `scales_input()`; captures that can scale for free honour the `set_output_size()` hint). Event-driven captures deliver nothing on a static desktop, so the worker keeps the newest frame: a frame skipped by FPS pacing is sent once the pacing allows, a REQUEST_KEYFRAME re-encodes it as an IDR at once, after a change or an IDR an inter codec re-encodes it as 30 P-frames at the paced rate (refinement: a still screen otherwise stays at the blurred quality an IDR or a moving frame got, ~30 dB PSNR on text against ~54 refined), and an idle stream re-sends it every second as a P-frame (keepalive; a lost last frame shows the client a gap there). There is no periodic IDR (the encoder GOP is a 60 s safety ceiling): each one blurred the picture again. VAAPI runs VBR, not CBR (Intel's iHD pads every CBR frame to bitrate/fps: 41 666 bytes per still 1080p frame at 20 Mbps). The `--stub` capture mimics that (one frame, then nothing), so the tests exercise this path. Keyboard `scancode` is a Windows VK code on every OS; `main.cpp` presses Shift/Ctrl/Alt around a key from the client's `modifiers` bits (the VR keyboard latches them locally), and non-Windows injectors translate VKs (`input/vk_keysym.h` for X11/Wayland, a kVK table in `mac_input.mm`).

Source layout: `capture/` (`wgc_capture.cpp`/`dxgi_capture.cpp` Windows, `mac_capture.mm`, `x11_capture.cpp`, `portal_session.cpp` + `pipewire_capture.cpp` for Wayland, `linux_backends.cpp` = which Linux backend runs, `stub_capture.cpp`), `encoder/` (`encoder.cpp` = MJPEG software path, `mf_encoder.cpp` = Media Foundation HW path for NVENC/AMF/QSV, `vt_encoder.mm` = VideoToolbox, `ffmpeg_encoder.cpp` = Linux NVENC/VAAPI/libx264; all obey the output contract documented in `encoder.h` — one access unit per `encode()`, Annex-B/OBU, parameter sets on every IDR, no B-frames, BT.601 limited), `network/` (`server.cpp` — TCP control channel, UDP packetisation and send, flow control), `input/` (`input_injector.cpp` SendInput, `mac_input.mm`, `x11_input.cpp`, `portal_input.cpp`), `driver/` (`idd_manager.cpp` — IDD virtual-display detection, see below), `audio/` (`audio_capture.cpp` WASAPI, `mac_audio_capture.mm`, `pulse_audio_capture.cpp`), `ui/` (the persistent UI, see `docs/ARCHITECTURE.md`: `host_ui.h` = live `Settings` atomics + the `Hooks` main.cpp lends, `panel.cpp` + `panel.html` = the settings page on 127.0.0.1 with token/cookie/Origin/Host checks — the page and the Grotesk font are embedded at build time by `embed.cmake`, `tray_win.cpp`/`tray_mac.mm`/`tray_linux.cpp` = tray icons, `ui_platform.cpp` = opening the app window and start at login (filesystem calls there use the `error_code` overloads: an unreadable `~/.config/autostart` means "off", never a crash), `ui_common.cpp` = host.conf, PIN file, second-launch handoff, the tray mark rasteriser). `src/` is on the include path for private headers shared between backends.

On a Wayland session capture and input share one process-wide portal session (`portal_session.cpp`, libdbus): RemoteDesktop+ScreenCast, persisted with a restore token in `~/.config/immersive2/portal-restore-token` so only the first run shows the dialog; X11 is never used as a silent fallback there (it would capture black). Virtual displays made on a headset's request (`IVirtualDisplayManager` in `driver/idd_manager.h`, ids from `VIRTUAL_MONITOR_ID_BASE` = 100, at most 4, removed on exit): X11 adds RandR 1.5 monitors (`x11_capture.cpp`, the screen grows to the right), GNOME Wayland uses Mutter's ScreenCast RecordVirtual (`mutter_virtual.cpp`), macOS the private `CGVirtualDisplay` looked up at run time (`mac_capture.mm`, untested: CI only compiles it), `--stub` fakes them in grey 208; Windows and other desktops answer VDISPLAY_UNSUPPORTED. IDD detection is Windows-only. The same manager darkens the main monitor on a headset's SCREEN_OFF (`set_primary_off()`; HOST_FLAG_SCREEN_OFF): X11 zeroes its CRTCs' gamma (XShm still grabs the picture; an all-zero ramp left by a killed host is lit at start-up), GNOME Wayland does the same through Mutter's DisplayConfig (`mutter_virtual.cpp`: GetCrtcGamma/SetCrtcGamma, and SetBacklight to the `Backlight` property's min on a laptop panel; Mutter restores its own ramp when monitors change, so every renewal re-applies it, and it restores both itself when the host dies; checked on GNOME 50: the screencast keeps the full picture), macOS zeroes the display transfer formula (untested), Windows 10 2004+ covers it with a black click-through topmost window excluded from capture (`WDA_EXCLUDEFROMCAPTURE`, its own message thread), `--stub` logs it, other Wayland desktops can't. `main.cpp` keeps it a lease: the client re-sends off = 1 every 2 s with its latency probe, and the screen is lit again 10 s after the last one, when that client leaves, in view-only and on exit (also on SIGHUP); every connection starts lit, and the client's switch (Connect tab) follows the host's SCREEN_OFF answers.

### IDD virtual display detection

`idd_manager.cpp` looks for a device whose hardware ID starts with `Root\VID_IDD` via `SetupDiGetDeviceRegistryProperty(SPDRP_HARDWAREID)`, with a secondary fallback check for any monitor device whose friendly name contains "virtual". If neither matches, `is_driver_installed()` returns false and the host just uses physical monitors — this is optional, not required for normal operation. `is_driver_installed()` is a pure query; the signature-trust bypass lives in `install_idd_signing_certificate()` and only runs from `--install-idd-cert`. Driver install/build instructions are in `docs/IDD_DRIVER.md` (it relies on a third-party community driver, `itsmikethetech/Virtual-Display-Driver`, and Windows test-signing).

### VR Client (Godot)

`client/project/scripts/main.gd` is the scene controller: connection state, auto-reconnect (to the last PC, following it via discovery if its IP changes), PIN pairing (pins per PC in the config's `[pairing]`), monitor selection, the arc arrangement / recenter (`pose_recentered` too), and automatic workspace persistence (layouts per monitor id, kept across STREAM_STOP/START so quality changes don't move screens; a saved layout far off the gaze is swung back in front). It is the only writer of `user://immersive2_config.cfg`. `host_discovery.gd` lists PCs from UDP broadcast replies. Automatic USB: on Android (or with `--im2-usb-port`) `usb_probe.gd` sends a HELLO to 127.0.0.1:<port> every 2 s unless already on the cable or the user pressed Disconnect; a HELLO_ACK makes `main.gd` move the session there (`_switch_to`, handled like a drop so screens stay), and losing the USB session falls straight back to `_lan_ip` (the PC's network address, which is also what the config keeps as `host_ip`). At launch it waits for the first probe before auto-connecting over Wi-Fi. The menu's status line says "over USB" / "over Wi-Fi". `screen_panel.gd` builds each screen's mesh itself — a flat quad or a cylinder section whose arc is `curvature × 1.75 rad` — and does the matching ray/cylinder hit test; the shaders only round the corners (no ALPHA write: screens are opaque). `laser_drag.gd` moves screens, menu and keyboard: by default rigidly locked to the pointer (the transform relative to it at grab time stays constant, position and rotation including roll; a roll or pitch within `LEVEL_DEG` of level eases flat), or, with the Input tab's "Screens face me while moving" on, the grabbed point stays on the ray and the thing turns to face the head (upright); reaching out/in with the hand pushes/pulls ×3.5; lightly smoothed; a screen group's other members follow rigidly. `grab_bar.gd` is the bar under each screen, the menu and the keyboard: trigger or pinch on it to move its owner. `resize_handle.gd` is a bracket outside each screen corner (shown when the ray passes near, zone outside the screen so the desktop's corner pixels stay the desktop's): `pick()` returns it as a `bar` hit, so grabbing it goes through the same `LaserDrag.grab()`, and dragging resizes the screen keeping its aspect ratio and the opposite corner fixed (width clamped to `ScreenPanel.MIN_WIDTH`..`MAX_WIDTH`, saved with the layout). `main.gd::pick()` is the one ray test both input paths use: the NEAREST of menu, keyboard, screens and bars. Screen groups ("Move together", per monitor, in the workspace JSON v3), the snap preview and "Lock screens in place" live in main.gd (`drag_group_for`, `snap_target_for`, `on_panel_drag_ended`, `can_move_panel`): while a screen is dragged near a free side of another (`SNAP_CAPTURE_M`), `snap_frame.gd` draws a thin white frame where it would land (`ScreenPanel.landing_beside()`, same orientation, a curved screen continues its arc), and releasing lands it there and from then on it follows that screen (`_snapped_to`, workspace JSON v4 `"snapped"`): moving that screen moves it and whatever follows it, moved itself it goes alone, dropped anywhere else it follows nobody; a resized screen keeps what follows it flush (`_reseat_snapped`), a removed virtual screen frees what followed it and a replaced one keeps its place; a screen with another right under it has its grab bar over its top edge (`_place_bars`), where the pointer can reach it. `match_virtual_screen(id, w, h)` replaces a virtual screen in place with one of any size (0 x 0: 1:1 for where it hangs, from `_headset_ppd()`): same spot, same width, or for a new shape that width rescaled as the shapes' defaults are. The size maths (shapes and presets, 1:1, how wide a new screen of each shape hangs, the H.264 envelope) is `virtual_size.gd`; the menu's size page (Screens tab "New virtual screen", or a virtual row's "Size", answered by `main.gd::_open_virtual_page()`) offers shape, orientation, presets, 1:1, ±128 px steps and any size on a keypad, with a to-scale preview and the pixels per degree against the headset's; the last size chosen is kept in the config's `[virtual]`. Auto quality uses the screen the pointer was last on. `world.gd` + `sky.gdshader`/`floor.gdshader` are the surroundings. `ui_theme.gd` holds the palette/type shared with the web page (Grotesk from Velvetyne, SIL OFL, in `fonts/`, for the wordmark and big titles only). `network_client.gd` rebinds its UDP socket to the `udp_port` in HELLO_ACK (the host's real port, not the config's) and forgives a gap in its own `_process` ticks (headset asleep) instead of declaring the host silent. `network_client.gd` owns the TCP control connection + UDP video/audio sockets and latency probing. Any host not on 127/8 is reached over `StreamPeerTLS`, `TLSOptions.client(cert)` with the PC's certificate as the only trust anchor (pinned), or `client_unsafe()` for a first contact, which sends no PIN and only learns the certificate from IDENTITY (`identity_received`; a failed pinned handshake emits `tls_failed(pinned)`); TLS is read one record at a time (`get_partial_data(1)` then `get_available_bytes()`: `get_partial_data(n)` keeps reading records until it has n bytes and throws all of them away if the host closes meanwhile, as it does after HELLO_REJECT). With a MEDIA_KEY, UDP video is received and opened (`SealOpener`, HMAC checked first in constant time) on a thread of its own (`_rx_loop`, started at HELLO_ACK, the only user of the UDP socket while it runs; SHA-256 is software in Godot's mbedTLS, ~12 µs a datagram on a laptop), and `audio_receiver.gd` opens audio with the same key. `main.gd` pairs (`docs/SECURITY.md`): certificates per PC in the config's `[pairing] certs` (keyed like the PINs); the PIN only goes to a connection pinned to the stored certificate or to the candidate a first contact showed, whose fingerprint the PIN prompt shows (`ui_overlay.show_pin_prompt(reason, who, code, changed)`); a failed pinned handshake makes the next connection a first contact: the same certificate carries on, another one gets the PIN prompt with a warning (`_candidate.changed`), and replaces the stored certificate only once a PIN typed for it is accepted; a PIN with no certificate (paired by an older version) is sent pinned to the first contact's certificate without asking; a certificate seen over the cable (plain, IDENTITY on request) is kept as that PC's. `screen_panel.gd` is a draggable/resizable 3D panel; `main.gd` owns one `video_decoder.gd` per monitor stream. `video_decoder.gd` wraps the `Im2VideoDecoder` Android plugin (MediaCodec) in a **zero-copy** path: MediaCodec decodes straight into a Godot `ExternalTexture` (a `GL_TEXTURE_EXTERNAL_OES` object) via a `SurfaceTexture`, and the panel's `screen_external.gdshader` samples it through `samplerExternalOES` — no CPU readback, no YUV unpacking. `SurfaceTexture.attachToGLContext`/`updateTexImage` must run on Godot's render thread, so they are scheduled via `RenderingServer.call_on_render_thread()` (driven each frame from `main.gd._update_decoders`). Each tick latches every frame pending in the SurfaceTexture (its queue can hold several and `updateTexImage` takes the oldest; the newest stays), and the codec is configured with `low-latency` plus Qualcomm's `vendor.qti-ext-dec-low-latency.enable` / `picture-order.enable` (the Pico 4 runs Android 10, before KEY_LOW_LATENCY), plain if refused; the `consumed frame` logcat line says how many frames were passed over and whether low-latency took. `VideoDecoder.is_codec_supported()` returns false without the plugin (PC/iOS/web); there `main.gd` instead opens a `SoftwareVideoDecoder` (`software_video_decoder.gd`) that decodes the MJPEG stream on a `WorkerThreadPool` thread and uploads the result via `screen_panel.gd::update_decoded_image()` — `_update_decoders` polls both decoder kinds each frame. `vr_input.gd` (one per controller; the last one whose trigger was pressed owns the pointer) / `hand_input.gd` handle controller and hand-tracking pointer input (the controller ray tilt and the pointing hand are Input-tab settings). A controller in use always wins: bare hands get the pointer only while `VRInput.any_in_use()` is false, i.e. every controller has been still for `IDLE_HIDE_S` (put down) or has no tracked pose, and picking one up or pressing its trigger/grip/button takes it back in the same frame. Picking up means moving `WAKE_MOVE_M` (3 cm) or turning `WAKE_TURN_RAD` (20°) against its rest pose smoothed over `WAKE_SMOOTH_S`: a controller lying on the desk drifts and, when the cameras find it again, its pose jumps in one frame (more than `JUMP_M` / `JUMP_TURN_RAD`); neither wakes it, and the log prints both (`picked up (moved … cm, turned …°)` / `its pose jumped …, ignored`). Hand joints alone decide nothing: the Pico reports them (source unknown) even while the controllers are held or lie on the desk, and with XR_EXT_hand_interaction's profile suggested it switched both sides to it and the controllers died, so the action map has no hand profile. Hand trackers are looked up every frame, never cached (Godot replaces them on a session restart). The hand ray runs from a shoulder (hanging off a neck pivot and a lazy torso yaw) through the index knuckle, One Euro filtered (min cutoff 0.5 Hz, beta 10), and the beam is drawn from the knuckle; a pinch already closed when the hand gets the pointer must open before it clicks. The other hand's palm turned to the face shows a menu mark; a short pinch toggles the menu. Both scripts print what the runtime reports when it changes (`[HandInput]` / `[VRInput]` in `adb logcat -s godot`); `ui_overlay.gd` is the in-VR menu (tabs Connect / Screens / Space / Quality / Input / Room, PIN keypad; holds no settings, main.gd pushes them in); `virtual_keyboard.gd` is the VR keyboard (a 2D UI in a SubViewport; one-shot Shift/Ctrl/Alt/Win, key repeat); `whiteboard.gd` is the whiteboard (Screens tab "Whiteboard", B on desktop; Line2D strokes in a SubViewport, kept in memory only): trigger/pinch on it draws, and `hand_input.gd` hands it each index fingertip through `main.gd::whiteboard_touch()` (within `HOVER_M` it owns the board and shows a ring, within `CONTACT_M` it draws, the pointing hand's ray rests meanwhile); its bar moves it and its corner `ResizeHandle`s resize it like a screen's (not blocked by "Lock screens in place"); key_map.gd` maps a Bluetooth keyboard's keys to VK codes (forwarded on Android only — on a PC client the keyboard already belongs to a PC). Controller vibration goes through the `haptic` action (action_type 4, `/user/hand/*/output/haptic` in every profile of `openxr_action_map.tres`) via `vr_input.gd::_buzz()`, gated by `main.gd::haptics_enabled`. `main.gd::_can_control()` (the user's "Control this PC" switch and the host's HOST_FLAG_VIEW_ONLY) gates every mouse/keyboard send. With "Sharper text" on and a runtime that composites layers natively, each `screen_panel.gd` drives an `OpenXRCompositionLayerCylinder`/`Quad` placed under XROrigin3D (fed from a SubViewport: the CPU texture, or the OES texture through `screen_layer_external.gdshader`), hole-punched behind Godot's projection layer, with its own mesh hidden (`layers = 0`) but still used for ray hits — untested on a headset, so it is opt-in. Virtual screens: the menu asks via VIRTUAL_DISPLAY_CREATE; `main.gd` shows the new monitor once both VIRTUAL_DISPLAY_RESULT and the re-sent MONITOR_LIST (per-monitor flags byte, MONITOR_FLAG_VIRTUAL) have arrived; `--im2-virtual=WxH` does that from the command line for tests; `audio_receiver.gd` decodes the UDP PCM audio stream into an `AudioStreamGenerator`.

The Android decoder plugin is a separate Gradle/Java project at `client/android-plugin/` (not part of the Godot project tree) producing an AAR consumed via the `addons/im2_decoder` export plugin (an `EditorExportPlugin` that adds the AAR via `_get_android_libraries`).

### Multiplayer rooms (client)

`room.gd` (class `Room`, node `/root/Main/Room` on every headset: its RPCs need the same path) is the room: Godot's SceneMultiplayer over `ENetMultiplayerPeer`, UDP `Room.PORT` 19820 (`--im2-room-port`). One headset `open()`s it (random six-digit PIN, or `--im2-room-pin`) and relays (server_relay); others `join()` with address + PIN, checked in `auth_callback` (five wrong ones lock an address out for a minute; a wrong one is answered with auth data `[0]` and the joiner leaves). The host also answers `HostDiscovery` requests on PORT + 1 (people count in the `monitors` byte, name = its person), and the Room tab runs a `HostDiscovery` on that port while it is shown. Everything is in the room frame (the Room node's, i.e. the world), not XROrigin3D, so people can move (see below). RPCs: `_take_profile` (reliable: name, mic, `share` = {ip, port, code} of their PC, `screens` = [{id, x: 12 floats basis+origin, w, c}], `board` = {on, x, w} their whiteboard), `_take_pose` (unreliable_ordered ch 1, 30 Hz: `Participant.pack_pose` = flags + head + both hands: a controller while `VRInput.in_use()` (one lying on the desk is still "tracked" on the Pico), else the XRHandTracker palm when its source is real, as hand_input.gd decides), `_take_ink` (reliable ch 3: ink on the sender's board as `[author peer id, op]` pairs, the ops being `Whiteboard.ink`'s `["b", colour, width, x, y]`, `["p", x, y]`, `["u"]`, `["c"]`; `Whiteboard.apply_ink(op, author)` keeps each author's current stroke apart and never re-emits what it replays; Room keeps every pair since launch, `_ink_log`, and sends it to whoever joins, in batches), `_draw_on` (reliable ch 3: a guest's ops on OUR board, applied if `pref(guest, "draw")` and passed on to everyone else; the guest drew them on its copy already, so it gets none back), `_take_voice` (ch 2: mic on a muted `RoomMic` bus with AudioEffectCapture, box-filtered to 16 kHz mono, 20 ms PCM-16, noise gate `GATE_RMS`/`GATE_HOLD_S`; `--im2-tone` sends a 440 Hz tone instead). Android asks for RECORD_AUDIO when the mic first starts (`audio/driver/enable_input` is on in project.godot; `permissions/record_audio` in the presets). Seats: everyone in one row by sorted peer id, `SEAT_SPACING_M` apart, same facing (`Room.seat()`); colours `UiTheme.PEOPLE` by seat. `participant.gd` (class `Participant`, one per other person, placed at their seat) builds the avatar (head with a headset visor and strap, shoulders + tapered chest turning after the head, mitts, Label3D name brighter while speaking), plays their voice from the head (AudioStreamPlayer3D on an AudioStreamGenerator, a 60 ms cushion when it ran dry, at most 0.3 s queued), validates every profile field (it is network input), replays their whiteboard (a `Whiteboard` of its own, `apply_ink`, shown where theirs hangs while theirs is shown and we see it; if their profile's `board.guests` lists us, what we draw on it goes to them, `Room.draw_on`; grabbed by its bar it stays where we put it), honours what we see and hear of them (`set_seen`: their board, their screens, off = no watch connection at all, their voice), and watches their PC: a second `network_client.gd` with `watch_code` (HELLO_FLAG_WATCH, its own ephemeral UDP port, latency probes every 2 s, over TLS pinned to the share's `cert`: a PEM that `X509Certificate` loads, else unpinned TLS), a `SoftwareVideoDecoder` per screen (the host sends watchers MJPEG; `VideoDecoder.show_on` puts it on the panel, as in main.gd), panels hidden until their layout arrives; a panel grabbed here (`main.pick()` returns remote surfaces as kind "remote", their bars as bars; `drag_group_for`/`on_panel_drag_ended` ignore them) stays where it was put. A refused watch waits for a new share; a lost one retries every 5 s. `main.gd` shares: the Room tab's switch (`share_screens`, never saved, `--im2-share`) + in a room + connected → a fresh WATCH_CODE to the host, then on the answer to the next latency probe (proof the host has it) `room.set_share({ip: _lan_ip or HELLO_ACK's lan_address, port, code, cert: the PC's certificate from IDENTITY})`, and every 0.5 s the screens' layouts (`room.set_screens`) and, in a room, the whiteboard's (`room.set_board`), each sent only when changed; whiteboard ink goes to `room.send_ink` every frame. Moving (main.gd `walk`/`turn`/`pull`/`back_to_seat`) carries XROrigin3D through the world: `vr_input.gd::_update_locomotion` makes the left stick walk (head-relative, `WALK_SPEED`) and the right one turn `TURN_STEP_DEG` about the head, only while the stick is free (not carrying something, not the pointer on a screen or the menu, where it scrolls); `hand_input.gd` turns a pinch on empty space into a pull (`_pull_at`, tracking-space positions so the moving origin does not feed back, `PULL_GAIN`); the Room tab's "Back to my seat" resets the origin. With "Sharper text", `_sort_layers` also asks `room.occluder_points()` (heads, chests, hands, corners of shared screens and boards) and a layered screen standing in front of any of them draws its mesh as well (`ScreenPanel.draw_mesh_over_layer`, hole punch off meanwhile): the punched hole let avatars behind it show through on the Pico. The menu's Permissions page (over the Room tab, one switch per person and column, aligned in a GridContainer, rebuilt only when people come or go so a switch is never swapped under a pointer) sets `Room.set_pref(id, "board"|"screens"|"voice"|"draw", on)`: the first three only for us, "draw" adds them to our profile's `board.guests`; this session only. main.gd's `pick()` returns a board that lets us draw as kind "whiteboard" (with `board`), else as "remote"; `send_whiteboard_pointer` / `whiteboard_touch` / `leave_whiteboard` go to the nearest drawable board (ours or theirs), and vr_input's grip moves the board it points at. `--im2-room=open|IP`, `--im2-name`, `--im2-board` (show the whiteboard and draw a line), `--im2-board-open` (whoever joins may draw on it), `--im2-draw-remote` (draw on the first board of someone else's that lets us), `--im2-no-mic` and `[Immersive-2][TEST] room …` / `remote panel …` / `remote board …` lines in `--im2-capture` drive and check it in e2e step 9.

Trying it alone: `python3 host/tools/room_sandbox.py [join IP PIN] [--tone] [--switch-host]` starts "Ben's PC" (a `--stub` host on TCP 19900) and Ben, the real client on the PC under `client/tests/room_bot.gd` (`/root/Main` from main.tscn plus fake XRControllerTrackers): he opens a room with PIN 111111 (or joins the headset's), shares two stub screens, looks at whoever is there, sways and waves, repeats what he hears 1.5 s later (`Room.voice_heard` / `say()`, deaf while speaking so the headset's speakers cannot loop it), draws six lines on his whiteboard through `pointer_ray` and lets whoever joins draw on it (`--im2-board-open`). ### Protocol

TLV control messages over TCP (`uint8 type, uint32 length LE, payload`), chunked binary frames over UDP (monitor id, frame number, chunk index/count, ≤1400-byte payload), each followed by 20 % XOR parity chunks (`VideoParityHeader`; `network_client.gd::_rebuild_chunk` rebuilds one lost chunk per group; `smoke_client.py` and `client/tests/fec_test.gd` pin the format from both sides). Over TLS every UDP datagram is sealed (`IV | AES-128-CBC | HMAC tag`, `docs/PROTOCOL.md` Sealed datagrams; `tls_test.py` and `client/tests/seal_test.gd` pin it from both sides). Default ports: TCP 19800 (control), UDP 19801 (video), UDP 19802 (audio, PCM-16 stereo 48kHz). All message types/struct layouts are defined once in `protocol/protocol.h` — extend that file first when adding a new message, then mirror the struct packing manually in GDScript (the client has no codegen from the header).
